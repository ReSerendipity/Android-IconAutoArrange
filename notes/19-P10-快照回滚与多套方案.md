## 1. 第 6 步：快照与回滚（`Snapshots`）

### 1.1 设计

- 每次 `openFile` 成功生成布局后，把 XML 另存到 `<filesDir>/snapshots/<时间戳>.xml`
- **最多保留 5 份**（超出按时间删最旧）
- **内容相同则跳过** —— 避免用户连点两次「应用」产生两份一模一样的快照
- 列表按时间倒序，标记哪一份等于当前基线（`current`）

### 1.2 回滚语义（必须写清楚）

`RESTORE_SNAPSHOT` = 把该快照写回 `last-generated.xml`，**下次生成即以它为合并基线**。

⚠️ 两个必须说明的限制：
1. **快照只含"本应用生成过的布局"**，不含用户手工拖动的结果（免 root 读不到 launcher 真实布局，见 `notes/10`）
2. **回滚的是「布局」，不是「配置」** —— 如果之后改过 Dock / 分类设置，回滚会按**当前设置**重新生成

第 2 点在实测中真的出现了：回滚后 Dock 变成 `Settings/Maps + 补齐`，而不是快照里的
`Chrome/Camera/Photos/YouTube` —— 因为 `dockMode=manual` 的**当前**设置仍然生效。
这不是 bug，但必须写在 UI 上（已写）。

### 1.3 实测

| 步骤 | 结果 |
|---|---|
| 第 1 次导入 | 快照 `1790997085848`（5 文件夹 / 20 应用，`current=true`） |
| 改配置再导（XML 相同） | **仍是 1 份** —— 去重逻辑正确跳过 |
| 换成完全不同的 Dock 再导 | **2 份**：新的 `current=true`，旧的 `current=false` |
| 回滚到旧快照 | ✅ `current` 标记转移，基线切换 |

## 2. 第 7 步：多套方案 Profile

### 2.1 关键设计取舍：**不做 key 命名空间化 + 迁移**

原计划是「所有配置 key 加 `profile:<id>:` 前缀 + 迁移历史数据」。但这要**重写整个配置存储层**，
是全部 10 步里回归风险最高的一处。

**改用的方案**：

> **方案 = 一份配置快照（JSON）；切换方案 = 把快照写回平铺 key。**

- `saveProfile(name)`：`toJson()` 当前配置 → 存 `profile:<name>`
- `loadProfile(name)`：取出 JSON → `applyJson()` 写回平铺 key（先清掉旧的 `ov:` / `cf:`）
- **完全不动现有的 key 布局，零迁移风险**

代价：切换是"写入式"的（改完配置需要再「保存」才会更新方案）。但这恰好是**可理解的预设语义**：
「保存当前配置为方案」/「应用方案」。

### 2.2 方案包含什么

Dock 设置（`dockMode` + `manualDock`）/ 排序策略（`folderSort`、`screenStrategy`）/
分类覆盖（`overrides`）/ 手动分组（`customFolders`）。

**不含**：网格（设备属性）、调试开关（开发用）、快照与基线（那是布局历史，不是配置）。

序列化用 Android 内置的 `org.json`（API 1 就有），省掉自己写解析器。

### 2.3 实测

| 步骤 | 结果 |
|---|---|
| 存「工作」 | `profiles=['工作']` |
| 改成 usage / 首屏常用优先 / 清空手动 Dock，存「极简」 | `profiles=['工作','极简']` |
| 切回「工作」 | ✅ `dockMode=auto, folderSort=name, screenStrategy=balanced, manualDock=[settings, maps]` **完整还原** |

## 3. 默认模式回归

| 模式 | 结果 |
|---|---|
| **full** | ✅ **逐字节一致**（与基线无关，是可靠信号） |
| merge | ⚠️ 本次与 `golden-before` 有差异 |

**merge 的差异不是回归**，而是**我测试时改动了基线本身**（回滚过快照）。逐行核对确认差异
全部来自"基线里的文件夹/dock 不同"，而非代码行为变化。

> ⚠️ **这是 merge 基线比对方法的一个固有性质**：`merge` 输出依赖当前的
> `last-generated.xml`，所以它是**有状态的**。要让 merge 也可复现，得先固定基线
> （例如用 `RESTORE_SNAPSHOT` 回到已知的一份）。
> **结论：`full` 模式（`forceFull=true`）才是与状态无关的可靠回归信号**，日常回归以它为准。

## 4. 遗留

- 方案切换是**写入式**的（改配置后需再保存）。若要做成"自动同步到当前方案"，需要在每次
  `setLayoutOption` 时回写方案 —— 会让"切换"和"编辑"语义混淆，暂不做。
- 方案不支持重命名（可以先另存再删）。
- **配置导入/导出（第 9 步）现在几乎是免费的** —— `AppConfig.toJson()` / `applyJson()`
  已经就位，只需加文件读写与分享 Intent。
- 未在真机验证；第 8–10 步待做。
