# 15 · 功能扩展路线图（深度思考）

> 日期：2026-10-02
> 背景：P0–P9 已完成（布局生成 / 增量合并 / UI / Shizuku 免 root 一键 / 手动分组）。
> 本文回答一个问题：**这个 app 接下来应该往哪走？**

---

## 一、先看清现状的本质

把已完成的能力排一遍，会发现它们其实是**同一件事的不同侧面**：

| 已有能力 | 本质 |
|---|---|
| 自动分类成组 | 决定「谁和谁在一起」 |
| 网格自适应排布 | 决定「放在哪里」 |
| 增量合并 | 决定「保留什么」 |
| 手动分组 / 改分类 / 排除 | 让用户**纠正**上面的决定 |
| 4 种应用方式 | 把决定**落地** |

**共同点：全都发生在「用户主动打开 app 并点击应用」的那一刻。**

所以当前产品形态的本质是 —— **一个「一次性整理器」**：
> 用户打开 → 调整 → 应用 → 关掉 → 用一段时间后桌面又乱了 → 再来一次。

### 三个由此暴露的根本短板

1. **决策依据太单薄**：现在只知道「这个应用属于哪个分类」，不知道「**它对用户有多重要**」。
   - 具体表现：**Dock 是硬编码的**（拨号/短信/浏览器/相机）。但真实用户最常用的可能是微信、支付宝、某个工作 IM。
   - 结果：排出来的桌面「看着整齐」，但**不好用**。

2. **完全依赖手动触发**：装一个新应用，桌面不会自己更新，用户得记得回来点一次。
   - 结果：**用几次就懒得用了**，桌面退回混乱。

3. **不可逆**：一键应用 = 覆盖现有布局，用户没有「先看看会变成什么样」和「不行就退回去」的余地。
   - 结果：**不敢按那个按钮**（尤其看到「会重置桌面」的红色警告时）。

---

## 二、扩展方向：三根支柱

把上面的短板反过来，就是三条主线：

```
        决策质量            自动化              可逆性
    （放得对不对）      （要不要手动）      （敢不敢按）
          │                  │                  │
     使用频率驱动        新装应用归位        变更 Diff 预览
     首屏策略可配        多套方案 Profile     快照与回滚
     文件夹命名/排序     定时整理            配置导入导出
     Dock 可配置
```

下面逐条展开，并标注**成本**与**依赖**。

---

## 三、支柱一：决策质量 —— 从「分类」到「个性化」

### 1. 使用频率驱动 ⭐ 最推荐

| 项 | 内容 |
|---|---|
| **做什么** | 用 `UsageStatsManager` 拿最近 7/30 天的使用时长与启动次数，据此决定：**首屏放谁、Dock 放谁、文件夹内谁排前面** |
| **为什么是质变** | 从「按名字归类」升级为「**按你的习惯排列**」。同一个 app，装在不同人手机上应该排出不同的桌面 |
| **可行性** | ✅ **已实测**：`appops set <pkg> GET_USAGE_STATS allow` 生效（之前对我们 app 失败只是因为没在 manifest 里声明 `PACKAGE_USAGE_STATS`）。用户侧走「设置 → 特殊应用权限 → 使用情况访问」，**免 root** |
| **成本** | 中（权限引导 UI + 频率排序逻辑 + 兜底：拿不到数据时回退到现在的行为） |
| **风险** | 模拟器/新机没有使用数据 → **必须做好降级**（无数据时按当前逻辑走） |

**具体可落地的三条规则**（由浅入深）：
- **Dock 改为「高频优先」**：不再硬编码，取使用时长 Top N
- **首屏「常用优先」**：高频的单图标/文件夹排前面
- **文件夹内排序**：按使用频率而非名称

### 2. 首屏策略可配

现在是「文件夹按成员数降序，塞满第一屏为止」。可扩展为几种策略：

| 策略 | 效果 |
|---|---|
| 均衡（现状） | 按分类大小平铺 |
| **常用优先** | 高频应用/文件夹进首屏（配合使用频率） |
| **分类分屏** | 社交一屏、工具一屏、娱乐一屏，不混排 |
| **极简** | 首屏只留高频几个，其余收进抽屉 |

### 3. Dock 可配置 ⭐ 低成本高收益

- 现在：硬编码优先级列表
- 改法：**直接复用「手动分组」那套勾选 UI** —— 勾选 N 个 → 作为 Dock
- 成本：**低**（数据层与 UI 都能复用现成代码）

### 4. 文件夹命名与排序可配

- 现在：分类名硬编码（效率/工具/影音/社交/出行/其他）
- 可加：自定义分类名（比如把「影音」改成「看片」）、文件夹内按频率/名称排序

---

## 四、支柱二：自动化 —— 从「手动触发」到「持续同步」

### 5. 新装应用归位 ⭐

**技术难点（必须诚实面对）**：让 launcher 重新读取布局的唯一手段是**重建它的数据库**（`pm clear`）。
为了"新装一个应用"就清空整个桌面数据库，**代价过重**。

因此现实的做法分三档：

| 档位 | 做法 | 体验 | 风险 |
|---|---|---|---|
| **A（推荐）** | 监听 `PACKAGE_ADDED` → 在 app 内累计「待归位」计数 → **角标提示 + 一键归位** | 用户知情、可控 | 低 |
| B | 检测到变化 → 发通知「3 个新应用待归位」 | 稍打扰 | 低 |
| C | Shizuku 常驻，静默重建 | 无感 | **高**（用户会失去控制感，且频繁清库可能触发 launcher 异常） |

**建议先做 A**：它把"自动化"的价值拿到了（用户不用记得），又不越过"用户知情"这条线。

### 6. 多套方案（Profile）

- 工作 / 极简 / 游戏 / 演示，一键切换
- 每套方案 = 一组规则 + 分组 + Dock 配置
- 复用现有的数据层（都是 SharedPreferences），加个 `profile:<id>:` 前缀即可
- **卖点性质**：让 app 从「工具」变成「产品」

### 7. 定时/条件整理

- 每周整理一次（WorkManager）
- 或「应用数量变化 > N」才提示
- **优先级偏低**：在 A 档（新装归位）做好之前，定时整理意义不大

---

## 五、支柱三：可逆性 —— 从「覆盖」到「可试错」

### 8. 变更 Diff 预览 ⭐ 低成本高收益

应用前明确告诉用户：

```
本次将：
  新增 3 个应用      （列出名称）
  移动 5 个位置
  移除 2 个失效项
  保留 4 个已有文件夹
  影响：屏幕 0~1
```

- 现在只有一行总数（`保留文件夹 4 个, 新增 1 个应用…`）
- **成本：低** —— 规划结果里已经有全部信息，只需要做「与上一次结果的对比」
- **价值：高** —— 直接降低"按下去会怎样"的焦虑

### 9. 快照与回滚

- 每次应用前，把当前（我们生成的）布局存成带时间戳的快照
- 支持「回到上一个布局」
- ⚠️ **限制必须写清楚**：免 root 读不到 launcher 的真实布局，所以快照只能基于**我们自己生成的版本**。
  用户手工拖动的改动**不在快照里**（这条与 `notes/10` 的结论一致）

### 10. 配置导入/导出

- 规则 + 手动分组 + Dock 配置 → 一个 JSON 文件
- 用途：换机迁移、分享给别人、备份
- **成本：低**（现有数据都已经是 key-value，序列化即可）

---

## 六、基础层：兼容与可靠

| 项 | 说明 | 优先级 |
|---|---|---|
| **网格探测** | UI 现在会显示「网格未知」直到 launcher 调用过一次。可加首次向导让用户选网格，或按屏幕尺寸/DPI 估算 | 中 |
| **厂商 ROM 验证** | 小米/华为/OPPO/vivo 的 launcher 是否保留 `launcher3.layout.provider` 通道 —— **完全未知**，是最大的产品风险 | 高（但需真机） |
| **Nova 等第三方 launcher** | 走无障碍服务（`notes/00` 的路径①/③），工作量**大**（要模拟拖拽、处理各种 UI 差异） | 低（先不做） |
| **应用图标 / 名称 / 首次引导** | 产品化收尾 | 中 |

---

## 七、优先级建议

| 优先级 | 功能 | 理由 | 成本 |
|---|---|---|---|
| **P0** | **使用频率驱动** | 唯一的**质变**项：从"分类"到"习惯"；免 root 已验证可行 | 中 |
| **P0** | **变更 Diff 预览** | 成本最低、收益最直接（降低应用焦虑） | 低 |
| **P1** | **Dock 可配置** | 复用现成勾选 UI，几乎零新增 UI 成本 | 低 |
| **P1** | **快照与回滚** | 与 Diff 配套，构成完整"可试错"闭环 | 低 |
| **P1** | **多套方案 Profile** | 从工具到产品 | 中 |
| **P2** | **新装应用归位（A 档）** | 自动化的最小可用形态 | 中 |
| **P2** | **配置导入/导出** | 换机 / 分享 | 低 |
| **P3** | 首屏策略可配 / 文件夹命名 / 网格向导 | 锦上添花 | 低-中 |
| **P3** | 厂商 ROM 验证 / Nova 支持 | 需真机或大工作量 | 高 |

**建议的第一步组合：`使用频率驱动` + `Diff 预览` + `Dock 可配置`**
—— 三者叠加后，产品体验会有可见的质变，且总成本可控。

---

## 八、明确**不**做的事（避免过度设计）

| 不做 | 原因 |
|---|---|
| **静默自动重排**（C 档） | 用户会失去控制感；频繁 `pm clear` 有风险。宁可"提示 + 一键" |
| **云端同步 / 账号体系** | 当前阶段没有真实需求，纯增加复杂度 |
| **主题 / 美化 / 图标包** | 不是核心价值，属于另一个产品 |
| **模拟用户拖拽（无障碍）** | 成本极高、脆弱；只在 Nova 支持时才考虑 |
| **AI 分类** | 先看规则引擎够不够用。分类准确度目前不是瓶颈，**排序质量**才是 |

---

## 九、一句话总结

> 现在这个 app 已经解决了「**能不能把桌面程序化重排**」。
> 下一步要解决的是「**排得好不好用**」（使用频率）、「**要不要每次手动**」（自动化）、
> 「**敢不敢按下去**」（可逆性）。
> 前者是技术问题（已解决），后三者才是产品问题。
