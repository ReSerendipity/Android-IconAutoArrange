> 日期：2026-10-02

> 产物：`UsageRank.java`（新增）、`LayoutPlanner` 三处策略接入、`AppConfig` 三个开关、UI 的「排序依据」区

## 1. 第 2 步：`UsageRank` 模块

### 1.1 打分

```
score(pkg) = 近 7 天前台时长(秒) × 1.0  +  近 8–30 天前台时长(秒) × 0.4
```

近期行为权重更高。数据源 `UsageStatsManager.queryUsageStats(INTERVAL_DAILY, …)`。

### 1.2 三层降级（**核心设计**：任何一层不满足都安全退回，绝不让排布出错）

| 情况 | status | available | 行为 |
|---|---|---|---|
| 未授权 | `未授权` | false | 用默认排序，UI 显示引导条 |
| 已授权但无记录（新机 / 模拟器） | `无数据` | false | 同上 |
| 有记录 | `可用` | true | 按 score 排序 |

`buildPlan` 里拿到 `usage` 后还会再判一次 `available()`，不可用就直接置 null —— **双保险**。

### 1.3 缓存

查询耗时可能 200–800ms，所以带缓存：内存 + `<cacheDir>/usage-cache.txt`，**TTL 30 分钟**。
格式用简单文本（首行时间戳，之后每行 `包名=分数`）—— 避免为了一个缓存引入 JSON 解析器。

### 1.4 只在真正用到时才查

```java
boolean needUsage = "usage".equals(cfg.dockMode)
        || "usage".equals(cfg.folderSort)
        || "usage".equals(cfg.screenStrategy);
UsageRank usage = needUsage ? UsageRank.load(ctx) : null;
```

默认配置下**一次查询都不做**。

### 1.5 权限

- manifest 加 `<uses-permission android:name="android.permission.PACKAGE_USAGE_STATS" />`
- 检查用 **appop**（`AppOpsManager.OPSTR_GET_USAGE_STATS`）而不是 `checkPermission` —— 这是 appop 型权限
- 用户侧：「设置 → 特殊应用权限 → 使用情况访问」，**免 root**
- 开发侧：`adb shell appops set com.example.layoutprovider GET_USAGE_STATS allow`

## 2. 第 3 步：三处策略接入

| 开关 | 取值 | 作用点 |

| `dockMode` | `auto`（默认）/ `usage` | Dock 候选顺序 |

## 3. 实测

### 3.1 造数据（模拟器没有真实使用记录）

用 `adb shell monkey -p <pkg> -c android.intent.category.LAUNCHER 1` **反复启动**来产生真实记录：

```
Chrome ×12 / Photos ×6 / Settings ×3
→ [usage] 查询完成，245 个应用，status=可用
```

### 3.2 三处策略都验证到了变化

**Dock**（全量模式下对比）：

| 模式 | Dock |
|---|---|
| `auto` | Phone / Messages / Chrome / Camera（硬编码优先级） |
| `usage` | **SpiritPal / Maps / Shizuku / Chrome**（按实际使用） |

**首屏槽位**：

| 模式 | 屏幕 0 的槽位 |
|---|---|
| `balanced` | 我的分组 / 其他 / 效率 / 工具 / Contacts / Maps |
| `usage` | 我的分组 / **工具 / 效率 / 社交 / 其他** |

**文件夹内**：

| 模式 | 「工具」文件夹内顺序 |
|---|---|
| `name` | Camera / Clock / Files / Settings |
| `usage` | **Settings / Camera / Clock / Files** |

> ⚠️ 注意：**合并模式下 Dock 变化不明显** —— 因为合并模式会**优先保留用户已有的 dock**
> （这正是设计意图），只有空位才用候选补齐。要看效果得用全量模式。

### 3.3 默认模式回归（关键）

| 模式 | 重构前 | 加了频率模块后 | 结果 |
|---|---|---|---|
| full | `f9214027…` | `f9214027…` | ✅ 逐字节一致 |
| merge | `44e59d51…` | `44e59d51…` | ✅ 逐字节一致 |

**默认配置下输出零变化**，新功能是纯增量。

## 4. ⚠️ 踩坑：我的回归工具有个隐蔽缺陷

第一次跑「加了频率模块后的默认模式回归」时，`full` 模式报了差异。排查发现 **不是代码问题，是工具问题**：

`capture-golden.sh` 早期版本用「把 `last-generated.xml` 临时挪走」来强制全量模式：

```bash
adb shell "cd /data/data/<pkg>/files && mv last-generated.xml _lg.bak"
```

**这条命令需要 root** —— shell(uid 2000) 进不了 app 私有目录。它之前能工作，只是因为
**adbd 恰好还是 root**（我在拉数据库时 `adb root` 过）。后来我在另一步结束时 `adb unroot`，
工具就**静默失效**了：`cd` 失败 → `&&` 短路 → 全量模式其实没生效。

**修法（两处）**：
1. 给 provider 加 `PLAN_JSON --extra forceFull:b:true` —— **免 root、确定性**地强制全量模式
   （顺带给 UI 留了「预览全量重建」的能力）
2. 脚本末尾**断言**实际拿到的 `mergeMode` 与预期一致，不一致就非零退出 ——
   避免"以为抓到了全量、其实是合并"这种静默错误

> **教训**：验证工具本身也需要断言。一个"看起来在工作"的测试脚手架，
> 可能因为环境变化（这里是 adbd 的 root 状态）而静默退化成什么都没测。

## 5. 数据质量：只列启动器应用

模拟器上实测 top1 是 `com.example.layoutprovider`（64623s）—— 那是开发期间我们自己的 app 长时间在前台。
这对用户是纯噪音，所以在 `planJson` 里 **`usageTop` 只列启动器应用**（先取 top40 再过滤）。

> 真机上这个列表就是用户真实的应用排行，不需要特殊处理；但**过滤掉非启动器应用**在任何设备上都是对的。

## 6. 遗留

- **频率排序在合并模式下对 Dock 影响有限**（设计使然：优先保留用户 dock）。要不要提供"即使合并也重排 dock"的选项，待定。
- **缓存 TTL 30 分钟**：用户刚改了使用习惯，最长 30 分钟后才反映。可考虑下拉刷新时强制重查。
- 未在真机验证（真机上的使用数据才是真实分布）。
- 第 4–10 步待做（见 `notes/16` §4）。
